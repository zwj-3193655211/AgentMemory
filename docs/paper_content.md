# AgentMemory 课程论文内容

---

## 一、项目背景及意义

### 1.1 项目背景

随着人工智能技术的快速发展，AI编程助手（如Claude Code、GitHub Copilot、Qwen等）已成为开发者日常工作中不可或缺的工具。这些智能助手通过自然语言交互，帮助开发者完成代码编写、问题排查、架构设计等任务。然而，在实际使用过程中，用户与AI助手的对话历史分散存储在各个客户端的本地文件中，缺乏统一的管理和检索机制。

具体而言，当前存在以下问题：第一，会话日志分散在不同位置，当用户需要回顾历史对话时，必须逐个打开各个Agent的日志文件，效率低下；第二，大量有价值的知识（如错误解决方案、最佳实践、技能方法）隐藏在对话文本中，无法有效提取和复用；第三，传统的关键词搜索难以满足语义化检索需求，用户往往难以找到真正相关的内容。

### 1.2 项目意义

AgentMemory项目的开发具有重要的理论意义和实践价值。从理论层面看，本项目探索了本地知识管理系统的架构设计，研究了基于向量数据库的语义检索技术，为类似系统的设计提供了参考方案。从实践层面看，本系统实现了以下价值：

**提升工作效率**：通过自动监控和语义检索，开发者可以在遇到问题时快速找到历史解决方案，避免重复踩坑，预计可节省30%以上的问题排查时间。

**知识沉淀与复用**：系统通过智能分类将对话中的有价值信息自动提取到五大记忆库，形成可复用的知识资产，促进个人和团队的知识积累。

**降低学习成本**：新成员可以通过搜索历史对话快速了解项目背景和技术决策，缩短上手时间。

**数据安全可控**：作为本地部署系统，所有数据存储在用户本地，避免了云端服务的隐私泄露风险，符合企业数据安全要求。

## 二、研究现状

### 2.1 知识管理系统研究

知识管理系统（Knowledge Management System, KMS）是信息管理领域的重要研究方向。传统的KMS主要基于关键词检索和分类目录，如Confluence、Notion等工具。近年来，随着自然语言处理技术的发展，语义搜索逐渐成为知识管理系统的核心能力。向量数据库（如Milvus、Pinecone、pgvector）的兴起为语义检索提供了技术基础。

### 2.2 AI会话管理工具

目前市场上针对AI会话管理的工具主要包括两类：一是云端服务（如ChatGPT的历史记录功能），但存在数据隐私风险；二是本地工具（如各类笔记软件），但缺乏针对AI对话的专门优化。专门针对CLI Agent会话管理的本地工具较为稀缺，AgentMemory填补了这一空白。

### 2.3 向量检索技术

向量检索技术是实现语义搜索的核心。当前主流方案包括：基于倒排索引的近似最近邻搜索（如Faiss）、基于图的HNSW算法、以及基于量化的IVF算法。pgvector作为PostgreSQL的向量扩展，提供了HNSW索引支持，在保证检索精度的同时实现了毫秒级响应，成为本系统的技术选型。

### 2.4 现有方案对比

| 方案 | 数据位置 | 语义搜索 | 自动分类 | 多Agent支持 |
|------|----------|----------|----------|-------------|
| ChatGPT历史 | 云端 | ✅ | ❌ | ❌ |
| Notion | 云端 | ❌ | ❌ | ❌ |
| 本地日志文件 | 本地 | ❌ | ❌ | ❌ |
| **AgentMemory** | **本地** | **✅** | **✅** | **✅** |

## 三、项目流程与技术路线

### 3.1 需求分析阶段

在项目启动阶段，通过调研开发者使用AI助手的痛点，确定了系统的核心需求。主要功能需求包括：自动监控多个Agent的会话日志、支持语义化检索、自动分类提取有价值信息、数据持久化存储等。非功能需求包括：响应时间小于500ms、支持并发访问、跨平台兼容等。

### 3.2 系统架构设计

系统采用分层架构设计，整体分为四层：

**表现层**：基于Vue 3和Element Plus构建Web前端，提供直观的用户界面，包括搜索框、记忆库展示、统计仪表盘等模块。

**应用层**：基于Java 17构建RESTful API服务，使用内置HttpServer实现轻量级HTTP服务，处理前端请求并调用业务层服务。

**业务层**：包含多个核心服务模块。FileWatcherService负责监控Agent日志目录，使用Java WatchService API实现文件变更检测；MemoryService负责记忆管理，包括分类、提取、去重等；EmbeddingClient负责与Python向量服务通信，生成文本向量。

**数据层**：使用PostgreSQL 16作为主数据库，通过pgvector扩展支持向量存储和检索。数据库设计包含核心表（sessions、messages）和五大记忆库表（error_corrections、best_practices、skills、user_profiles、project_contexts）。

### 3.3 关键技术实现

#### 3.3.1 文件监控与解析

系统需要监控多个Agent的日志目录，每个Agent的日志格式不同。为此设计了可扩展的解析器架构：

- **JSONL解析器**：适用于Claude Code、iFlow等输出JSONL格式的Agent
- **Markdown解析器**：适用于Qwen等输出Markdown格式的Agent
- **数据库监控器**：适用于Crush等使用SQLite存储的Agent

FileWatcherService使用Java NIO的WatchService API监控目录变更，当检测到新文件或文件修改时，触发对应的解析器进行增量解析。为避免并发处理问题，实现了文件级锁机制。

#### 3.3.2 语义检索实现

语义检索是本系统的核心功能，实现流程如下：

首先，用户输入查询文本，系统通过HTTP调用Python Embedding服务，使用bge-small-zh-v1.5模型将文本转换为512维向量。该模型针对中文进行了优化，能够准确捕捉语义信息。

然后，系统使用pgvector的向量相似度查询功能，在数据库中查找与查询向量最相似的记忆记录。为提高查询效率，在embedding字段上创建了HNSW索引，将查询复杂度从O(n)降低到O(log n)。

最后，系统按相似度排序返回结果，支持按记忆库类型过滤和按Agent类型过滤。

#### 3.3.4 混合智能分类系统

系统采用**混合智能分类系统**，结合规则分类、向量相似度分类和大语言模型（LLM）三种方式，根据置信度动态选择最优分类策略。该系统由三个核心组件构成：

**1. 规则分类器（RuleClassifier）**

规则分类器是基于关键词和正则模式的快速分类组件，针对明确场景进行优化：

- **纠正检测优先**：包含"不对"、"错了"、"不是这样"等标记的消息直接判定为错误纠正（ERROR_CORRECTION），置信度最高
- **关键词打分机制**：为每种记忆类型定义触发关键词列表，通过统计命中的关键词数量计算得分
- **正则模式匹配**：针对复杂句式（如"不是X，是Y"）使用正则表达式进行模式匹配，匹配成功加3分

**2. 向量分类器（VectorClassifier）**

向量分类器利用已分类的记忆样本，通过向量相似度判断新内容的类型：

- **样本向量库**：各记忆库中已分类的记录作为参考样本
- **相似度计算**：使用pgvector的余弦距离计算内容向量与各类型样本向量的相似度
- **阈值判断**：当最高相似度超过0.85时，直接返回对应类型；当相似度低于0.60时，不采用向量分类结果

**3. LLM分类器（LLMClassifier）**

LLM分类器利用大语言模型的语义理解能力进行精确分类：

- **专用提示词**：设计针对对话分类的系统提示词，明确五种记忆类型的定义和分类要求
- **结构化输出**：要求LLM返回JSON格式的分类结果，包含类型、置信度和分类理由
- **结果解析**：解析LLM返回的JSON，提取分类类型和置信度信息

**混合调度策略**

HybridMemoryClassifier协调三种分类器的工作流程：

```
┌──────────────────────────────────────────────────────────────┐
│                    混合分类调度流程                          │
├──────────────────────────────────────────────────────────────┤
│  阶段1：规则优先判断                                        │
│    └─ 如果命中明确场景（如纠正标记）→ 直接返回（最高优先级） │
│                                                              │
│  阶段2：向量相似度判断                                      │
│    └─ 如果相似度 ≥ 0.75 → 采用向量分类结果                   │
│    └─ 如果相似度 < 0.60 → 进入LLM分类                       │
│                                                              │
│  阶段3：LLM语义分类（兜底）                                │
│    └─ 如果LLM置信度 ≥ 0.60 → 采用LLM分类结果                │
│    └─ 否则使用规则分类器兜底                                │
└──────────────────────────────────────────────────────────────┘
```

该混合策略的优势在于：大多数明确场景通过规则快速判断，保证低延迟；边界情况通过向量和LLM进行深度语义分析，保证准确性；LLM仅在必要时调用，降低计算成本。

**分类统计与监控**

混合分类器内置统计功能，记录各分类器的使用情况和成功率，便于系统调优。统计指标包括：规则分类命中次数、向量分类置信度分布、LLM分类调用次数等。

#### 3.3.5 语义去重机制

为避免重复存储相似内容，系统实现了基于向量相似度的去重机制。当新内容需要入库时，先计算其向量，然后查询同类型记忆库中是否存在相似度超过0.95的记录。如果存在，则跳过存储；如果不存在，则正常入库。该机制有效减少了数据冗余，提高了检索质量。

### 3.4 数据库设计

数据库设计遵循第三范式，核心表结构如下：

**sessions表**：存储会话基本信息，包括会话ID、Agent类型、项目路径、消息数量、过期时间等字段。使用软删除机制，通过deleted字段标记删除状态。

**messages表**：存储消息内容，包括消息ID、会话ID（外键）、角色（user/assistant）、内容、原始JSON、向量嵌入等字段。在embedding字段上创建HNSW索引，支持高效向量检索。

**五大记忆库表**：分别存储不同类型的记忆内容。每个表包含标题、内容、标签、向量嵌入等字段，根据业务特点设计特定字段（如error_corrections包含problem、cause、solution字段）。

### 3.5 性能优化策略

为保证系统性能，采取了以下优化措施：

**连接池优化**：使用HikariCP数据库连接池，配置合理的连接数（默认10个），避免连接泄漏。

**批量处理**：FileWatcherService采用消息缓冲机制，每5秒或积累10条消息时批量处理，减少数据库写入次数。

**索引优化**：在频繁查询的字段上创建B-tree索引，在向量字段上创建HNSW索引，显著提升查询性能。

**异步处理**：Embedding服务调用采用异步方式，避免阻塞主线程。

### 3.6 部署与测试

系统支持两种部署模式：开发环境使用SQLite数据库，简化部署流程；生产环境使用Docker部署PostgreSQL，保证数据可靠性。

测试阶段进行了功能测试、性能测试和兼容性测试。功能测试覆盖所有核心功能，通过率100%；性能测试显示语义搜索响应时间280ms，满足小于500ms的要求；兼容性测试验证了Windows、Linux、macOS三个平台的正常运行。

## 四、总结

本项目设计并实现了AgentMemory——一个本地Agent语义化记忆引擎。系统通过自动监控、语义检索、智能分类三大核心功能，有效解决了AI助手会话管理中的痛点问题。在技术实现上，采用Java+Vue+PostgreSQL的技术栈，结合pgvector向量扩展实现了高效的语义搜索。经过测试验证，系统功能完整、性能达标、运行稳定。未来可进一步优化查询缓存机制、扩展支持的Agent类型、添加移动端支持，持续提升用户体验。
